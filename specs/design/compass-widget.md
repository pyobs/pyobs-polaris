# Compass widget for `TelescopeView.qml`'s Move fields

Status: implemented, closed.

Previously listed as deliberately out of scope (TODO.md's own "jog/compass widget" MVP scope cut) - shipped as a direct follow-up ("compass move widget now"), the last of `telescopewidget.ui`'s original four side-by-side GroupBoxes (Status/Move/Offsets/Compass) to land.

`compassmovewidget.py`'s own `__move_offset()` has a two-branch fallback: if the module reports `IOffsetsRaDec`, nudge that offset directly in ra/dec terms; else, if it reports both `IOffsetsAltAz` *and* `IPointingAltAz`, convert the compass's sky-relative N/S/E/W step into an alt/az-frame offset (needs the current alt/az pointing to know which direction on the sky "up" currently corresponds to in alt/az terms) via astropy's `spherical_offsets_by()`/`spherical_offsets_to()`. `TelescopeView.qml`'s new `moveCompass(direction)` (on `telescopeDelegate`, alongside `run()`/`runWithParams()`) ports the same two-branch fallback and the same "read current cumulative offset, add/subtract the step, send the whole new absolute offset" semantics (matching this project's own existing Offsets GroupBox, which already works this way rather than pyobs-core having any genuine incremental-jog RPC).

The ra/dec branch is a direct, exact port - no coordinate math needed, just `dec += step`/`dec -= step`/`ra += step`/`ra -= step` on whatever `raDecOffsetsState` already holds, then `set_offsets_radec`. The alt/az branch is **not** an exact port: astropy's `spherical_offsets_by()`/`spherical_offsets_to()` aren't available here, so it's approximated via a two-point difference through `CoordinateTransform`'s existing libnova-backed `horizontalToEquatorial()`/`equatorialToHorizontal()` (the same singleton the Move destination-coordinate preview already uses) - convert the current alt/az offset to an equivalent ra/dec delta at the telescope's current pointing, apply the step in ra/dec terms, convert back. Accepted as good enough because this branch is schema-verified only regardless of exactness: no built-in `Dummy*` module implements `IOffsetsAltAz` (same caveat the existing Offsets GroupBox's own Alt/Az row already carries - see `specs/design/itelescope-follow-up-libnova-destination-coordinate-preview.md`), so there's no live path to tell an exact port from a close approximation apart anyway.

**Button layout diverges from `compassmovewidget.ui`'s own grid on purpose**: that file places `buttonOffsetEast` in the *left* column and `buttonOffsetWest` in the *right* column (confirmed directly from the `.ui` XML - not a transcription error). pyobs-gui's own working notes (`DEV_telescopewidget_layout.md`, "Open questions to resolve before implementing anything") flag this exact placement as unresolved - "Could be intentional (some telescope/eyepiece/guider views mirror east-west), could be a leftover icon swap" - and it was never resolved upstream before this port happened. With nothing concrete to port faithfully either way, and no eyepiece/guider view in this project to check orientation against, this shipped as a standard compass rose instead (N top, S bottom, E right, W left) - the less surprising default for a control panel, not a sky projection.

Step spinbox (`compassStepSpin`) matches `compassmovewidget.ui`'s own `spinOffset` exactly: 0-999 arcsec, step 10, default 30. No `suffix` property attempt (QtQuick Controls' `SpinBox` has no such property, unlike `QSpinBox` - would need a custom `textFromValue`/`valueFromText` pair) - a plain "Step [arcsec]" label above it instead, matching the existing Offsets GroupBox's own "RA/Dec [arcsec]" label convention. All four buttons colored blue like Move, matching `compassmovewidget.py`'s own `colorize_button(..., QtCore.Qt.GlobalColor.blue)` calls for all four (same semantic-color pass the Move/Init/Park/Stop buttons already got - see this file's earlier "Color-code Telescope page buttons" entry).

**Verified live** against the real `fixtures/telescope.yaml` `DummyTelescope` (which implements `IOffsetsRaDec`/`IPointingRaDec`/`IPointingAltAz`, exercising the ra/dec branch - the alt/az branch stays schema-verified only, as explained above). Rather than simulating actual mouse clicks (no input-automation tool was available in this session, and installing one for synthetic system-wide input didn't seem like a proportionate risk for a single verification pass), verification used this project's own established "temporary hook, exercised once, removed before committing" precedent (same one `JplHorizonsClient`'s live verification used): a temporary auto-connect in `LoginWindow.qml`'s `Component.onCompleted` plus a temporary `Timer` in `MainWindow.qml` that navigated to the Telescope page and issued the exact RPC `moveCompass("E")`'s ra/dec branch would (`set_offsets_radec(30/3600, 0)`), both removed again immediately after. Confirmed via screenshot: the Compass GroupBox rendered in the correct position (after Offsets, before the Filter/Focus/Temperatures sidebar) with the N/W/step/E/S layout described above; the RPC returned `{"success":true}`; the log footer showed the real module's own `"Moving offset dra=0.00833, ddec=0.00000"` line; and the Offsets GroupBox's RA/Dec fields updated to `30`/`0` via the real server-pushed state - confirming the full chain (QML → `executeMethod` → real `DummyTelescope` → state push → back into the same fields the Offsets GroupBox already displays) works together, not just each piece in isolation.
